## 研究发现
- 当前仓库约有 4.6 万行设计文档，存在两轮跨文档一致性审查与大量旧 ADR；新体系必须减少重复定义并建立单一权威来源。
- 当前工作区已有多个代码文件处于删除状态，本任务不得恢复或修改这些文件。
- 旧文档覆盖了总体架构、领域事件、SQLite、权限、Context、DAG、扩展、部署等主题，可作为问题清单和反例来源，但不再作为目标约束。
- 已将根 `README.md` 和 27 份旧设计文档完整移动到 `docs/archive/legacy-2026-08-11/`，没有删除内容。
- AiAgent 横向分析验证了“单核多前端”应将业务状态集中在 transport-agnostic Core，客户端只消费命令、查询和事件；Reasonix 与 opencode 是可借鉴的独立收敛样本。
- Reasonix 的 write-path claim、父 Agent 写路径预留和嵌套请求 fail-fast，与本项目已确认的共享工作区并发模型高度吻合。
- MiMo-Code 的 Checkpoint-first、章节级校验与内容 spillover，可用于实现本项目的 `checkpoint.md` 清单 + 内容寻址片段事实源。
- opencode 的类型化 Context Source/Epoch 模式可用于区分稳定前缀、运行中更新和失效替换，避免把上下文变化散落在 Agent Loop 中。
- Reasonix 的 `SnipHinter` 模式说明裁剪策略应成为 Tool 契约的一部分，而不是集中式硬编码；这与 70% snip 阶段直接相关。
- 多项目实现共同暴露了 MCP stdio 进程树清理、OAuth state/回环绑定、项目会话租约和子 Agent 完成结构化回执等隐性必需契约。
- 参考项目普遍采用旁路 Git 快照，但用户已明确选择纯内容寻址文件 Snapshot；新设计只借鉴“文件回滚与对话历史解耦”，不采用 Shadow Git。
- QuickJS 确定性工作流是成熟路线，但用户已明确选择声明式 YAML DAG；新设计将以版本化 DAG IR 和纯数据调度决策替代脚本 VM。
- DeepSeek-TUI 的实际迁移状态表明“大 crate 逐步拆分”容易出现双重事实源；Apex 新 Workspace 必须从第一天规定依赖方向，并禁止客户端或旧运行时保留平行业务实现。
- DeepSeek-TUI 的 Runtime Thread 使用单调事件序列和 `since_seq` 重放，适合作为 Apex 的 Snapshot + Replay + Live 跨端实时协议基础。
- pi-agent 明确区分 AgentMessage 与 LLM Message，并在 Tool 并行执行时保持持久化 ToolResult 的源顺序；Apex 应将 UI/运行态消息与 Provider 线消息分层，禁止直接共用一个枚举。
- pi-protocol 将权威 Snapshot 与瞬态 Progress Event 分开，验证了实时 UI 提示不能被 Reducer 当作领域事实；Apex 协议也需要 Durable/Transient 两类事件。
- claude-code-rust 的 NDJSON bridge 与平台包发布模式证明“稳定 Wire 协议 + 私有子进程运行时 + 多平台不可变制品”可行，但 Apex 已选择本地 gRPC，因此只借鉴协议版本、诊断通道和打包校验思路。
- 参考实现的 Hook/LSP 流水线说明 PostToolUse 应先完成轻量同步门，再将重型诊断作为下一次 Provider 调用前的 barrier 注入，避免 UI 或 Agent Loop 与磁盘/语言服务器直接耦合。
- opencode V2 将 Prompt admission 与执行分离：先持久化 inbox，再由串行 Session Runner 提升为可见消息；这一模式适合 Apex 的多客户端输入、控制租约和崩溃恢复。
- opencode 在进程重启后会把遗留 `running` Tool 标记为 interrupted，且不盲目重放副作用；Apex 应把“不确定副作用”作为独立 BlockReason。
- Context Epoch 的初始化失败不会消费待处理 Prompt，说明外部上下文观察、Markdown 同步和 Provider 调用之间需要明确的安全边界与可重试 admission。
- Provider-native reasoning/continuation metadata 只能在模型兼容时重放；模型切换后必须降级为普通可见文本并剥离专属 continuation 标识。
- Reasonix 的实际源码把 write claim、调度器和 SnipHinter 分成独立契约；Apex 也应避免将路径互斥、Tool 输出裁剪和 Agent Loop 混成一个 crate。
- CodeWhale 的授权顺序、精确拒绝 key 与 arity-aware 批准 key 提醒：批准与拒绝的记忆粒度不应相同，拒绝必须更精确，批准必须受资源范围约束。
- Reasonix 的路径实现会解析最深已存在祖先并拒绝悬空 symlink，且在 macOS/Windows 做大小写折叠；Apex 的 PathScope 规范必须把不存在目标、符号链接和大小写不敏感文件系统写入契约测试。
- Reasonix Scheduler 的 FIFO waiter 会跳过暂时冲突项并启动后续可运行项；Apex 需要定义“公平但避免队首阻塞”的 Ready Queue，而不是简单全局 Mutex。
- CodeWhale 的授权流水线证明权限只能单调收紧：模式、Hook、工具基线、静态规则、安全底线、用户批准、运行时沙箱按固定顺序组合，后层不得抹去前层的 Deny/Hold。
- MiMo-Code 的 Checkpoint 模板将 Active Intent 保留为用户原文引用，并给每章节独立预算；Apex 的 Checkpoint Manifest 也应区分原文意图、派生状态和内容引用，避免摘要改写用户意图。
- Checkpoint Validator 使用 `warn/error/extract-required`，其中超预算要求拆出外部片段而不是继续压缩主文件；这与用户确认的内容寻址片段模型完全一致。
- MiMo-Code 的阈值 writer 锁和“跨过阈值只触发一次”状态可避免 Checkpoint 风暴；Apex 虽采用固定 60/70/80/90 阈值，仍需持久化 crossed-watermark 和失败重试门。
- 旧 Apex 总体架构把 daemon、runtime、storage、protocol、extension 的职责都列出，但同一事实在总册、分册和 ADR 中被重复定义，且缺少可执行的依赖方向约束；新设计必须用“需求权威 → 架构权威 → 契约权威 → 主题说明”的单向引用替代复制粘贴。
- 旧 Apex 领域模型与 API 文档对同一状态、事件和错误存在命名/版本漂移，审查文档虽记录了回写动作却未形成机器可检的注册表；新设计必须集中定义 ID、状态枚举、事件信封、错误命名空间与兼容规则，并把跨文档一致性检查列为交付门。

## 技术决策
| 决策 | 理由 |
|------|------|
| 新文档采用分层权威体系 | 防止需求、架构、协议和实现计划重复定义同一契约 |
| Markdown/文件系统与 SQLite 使用明确的分域事实源 | 满足可审计性，同时支持高效查询、调度和跨端同步 |
| 运行态最小事件与详细日志分离 | SQLite 负责状态重建，文件日志负责诊断和离线审计 |
| 关键安全保证必须描述技术边界 | 避免对进程内 Plugin、静态命令分析等能力作虚假承诺 |
| 新文档设四级权威层 | `01-requirements` 定义 What，架构/领域定义边界，Trait/协议定义稳定契约，主题文档只解释流程并引用权威项 |
| ADR 只保留索引和不可逆取舍 | 避免在 ADR 与主题文档重复维护完整方案；主题文档通过 ADR ID 引用取舍依据 |
| S10 必须拆成 TUI / Desktop / Web 三个独立执行轨道 | 用户要求三端分开实现，且 TUI 必须先完成完整功能并先给出测试 demo |
| TUI 测试 demo 必须置于正式 TUI 功能之前 | 这样能先验证连接、状态流、Reducer 和基础交互，再展开完整面板与编排功能 |
| Desktop/Web 只能依赖已冻结的 TUI 核心契约 | 避免三端一起推进导致共享协议和 UI 事实源重新耦合 |
| 共享前端安全规则不应隐式依赖 Web 专属认证 | 否则会把共用底座和 Web 轨道重新绑死，违背分轨顺序 |
| 高层路线图需要明确 TUI 优先而非三端并行 | 否则容易把实施波次误读为客户端并发开发 |

## 遇到的问题
| 问题 | 解决方案 |
|------|---------|
| 旧文档数量大且重复度高 | 先建立索引和主题提取，再只读取与新设计相关的权威段落 |
| 多处旧设计已与用户新决策冲突 | 用户确认的需求基线优先，旧文档仅提供风险和方案参考 |
| 参考实现偏好 Shadow Git，而用户选择纯文件 Snapshot | 使用内容寻址块、Manifest、原子 Capture 和补偿式 Restore 保持可逆性 |
| 参考实现多只完整支持 Bash | Apex 必须为 POSIX、PowerShell、Cmd 建立独立解析适配器和共同语义 IR |
| 参考项目常把 UI progress 与持久事件混合 | 协议层区分 DurableEvent、TransientEvent 和 QuerySnapshot，Reducer 只消费权威类型 |
| 多客户端输入可能在执行中到达 | 使用 durable inbox + steer/queue delivery，Session Actor 在安全边界提升输入 |
| 路径声明包含尚未创建的文件 | 解析最深已存在祖先并校验 symlink/大小写边界，再形成规范 PathScope |
